# v0.4 Benchmark expansion plan (design only)

No new benchmark tasks are generated in v0.4-B. The 96-task v0.3-B frozen dataset and
its 13 IID Validation / 13 IID Test / 18 OOD Test tasks remain unchanged.
31 held-out Test tasks support only preliminary per-mechanism results, not strong generalization claims.

## Proposed independent release

- Version: recovery-benchmark-v0.4-1; seed: 1042, separate from frozen seed 42.
- Target: IID Validation 40, IID Test 80, OOD Test 80 (200 total).
- New version directory, immutable generation config, manifests and file SHA-256.
- Train tasks, 204 Oracle decisions, 84 trusted Teacher decisions, and all 33 Teacher
  source episodes are exclusion inputs only. Test trajectories are never negative mining inputs.
- Each task keeps the existing Task structure: goal, initial_state, sqlite_initial,
  failed_action, fault, expected, allowed_resources, reference_plan, max_recovery_steps,
  mechanism_id, split, eval_group and dataset_version. No new execution engine or tool is required.

## Mechanism separation and meaningful state variation

IID retains the 13 existing Train mechanisms; Validation/Test have disjoint concrete state,
dependency and fault-position combinations. OOD retains the three mechanisms already held out:
git_compensating_commit, sqlite_dependency, sqlite_relink. Do not relabel a filename variant
as a new mechanism or introduce an OOD mechanism already represented in SFT/Teacher sources.

| Domain | Meaningful variation, within current tools | Required recovery evidence |
| --- | --- | --- |
| Git | stage/worktree disagreement at different dependency boundaries; correct vs stale HEAD preconditions; branch mismatch plus path conflict; multiple required files staged in distinct initial combinations | correct version/branch/content/index/commit plus complete allowed-resource ledger |
| SQLite | FK parent/child dependency placement; uniqueness occupancy and temporary allowed values; pending rollback/read state; operation order and duplicate-write preconditions | every required row/constraint and unchanged unrelated resources plus audit quotas |
| Mixed | different DB-derived report dependencies, initial report/index/HEAD mismatches, stale staged report while DB is already repaired | causally derived value, correct committed report, no unauthorized DB/file mutation |

Candidate combinations must be executable with the current fixed schemas, restricted SQL
and isolated Git/SQLite environments. More complicated recovery is not accepted just to meet quotas.
New task contracts may describe new benchmark states, but existing frozen contracts are untouched.
A mechanism is defined by the failure trigger and required causal recovery operations, not names/numbers.

## Future generator interface (not an implemented CLI)

    BenchmarkSpec(
        version="recovery-benchmark-v0.4-1",
        seed=1042,
        iid_validation=40, iid_test=80, ood_test=80,
        mechanism_partition=...,
        state_axes=...,
        exclusion_manifests=[frozen_manifest, delivery_manifest, teacher_source_hashes],
        max_recovery_steps=12,
    )

    propose_candidates(spec) -> Iterator[Task]
    canonicalize_state(task, erase_identifiers=True) -> StateDependencySignature
    certify_candidate(task) -> Certification
    freeze_benchmark(certified_tasks, spec, output_new_directory) -> Manifest

Certification runs the existing Oracle in the actual isolated environment, checks the
unchanged Verifier and audit contract, and replays the resulting trajectory. Keep no candidate
that fails, exceeds budget, is ambiguous or shares a concrete recovery/state signature with
training or another split. Record reject reasons rather than silently replacing/repairing tasks.
Reference plans and expected state stay private; visible goals must contain sufficient requirements.

The future certification adapter may attach a new dataset-version envelope to existing runner
outputs; it must not mislabel new tasks as the current hardening.VERSION (0.3-B). The present
evaluate_local_model.py intentionally accepts only the existing frozen release. A future dataset
reader must validate the new independent manifest rather than reusing the v0.3-B frozen validator blindly.

## Manifest and leakage gates

Record seed, generator code/config hash, task file hashes, mechanism partition, state-axis
coverage, canonical state/dependency signatures, Oracle lengths, complete verifier/replay
results, tool schema hash and exclusion-source fingerprints. Normalize IDs/filenames and
numeric scale when checking cross-split duplicates; exact task IDs alone are insufficient.
Report actual independent mechanisms, concrete instances and parameter variants separately.

Mechanism coverage should set minimum quotas but not fabricate certification success.
OOD mechanisms stay excluded from training, checkpoint selection and prompt tuning.
IID Validation alone supports configuration/checkpoint selection; only the selected fixed
configuration is run on IID Test/OOD Test. Do not aggregate several prompt experiments as
independent tasks.

## Evaluation protocol

Base and SFT use identical tasks, original initial state, tool schemas, prompt protocol
termination-v0.3c-2, max tool/request/token budgets, decoding seed/temperature and disabled
runtime-assisted stop. Compare comparison_signature before interpreting gains. Save model
weight/adapter hashes and software environment separately.

Report complete final success, ever full success, autonomous completion, actual unauthorized
mutation and quota-exceeding episode rates, invalid attempt rate, post-success calls,
per-episode tool/token overhead and request latency with explicit denominators. Provide
per-mechanism numerator/denominator, not only the global average; confidence intervals are
a future reporting choice after sufficient independent states exist.
